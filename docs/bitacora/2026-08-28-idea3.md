# 2026-08-28 — Idea #3: extender proxmox-mcp-server a Docker

## Contexto
Hasta ahora el LXC 101 "docker-host" era una caja negra — se veía como un solo contenedor Proxmox, sin visibilidad de lo que corre adentro (Portainer, AdGuard, Tailscale). Objetivo: dar visibilidad real por contenedor Docker individual.

## Decisión de acceso: API de Portainer, no Docker socket ni SSH
Se descartó exponer el socket de Docker por TCP (superficie de ataque innecesaria) y SSH directo (credencial adicional que administrar). Portainer ya corre ahí administrando ese Docker — se reusa su API REST con un usuario dedicado (`mcp-agent`), mismo criterio de credenciales dedicadas que Proxmox/Nextcloud.

## El problema real: Portainer CE no tiene RBAC granular funcional
Se intentó, en orden, dar acceso de solo lectura real a `mcp-agent`:
1. **RoleId 4 ("Read-only user")** en `UserAccessPolicies` del environment → el usuario ni siquiera veía el environment listado.
2. **RoleId 3 ("Standard user")** → veía el environment, pero `containers/json` devolvía `[]` vacío.
3. **RoleId 1 ("Environment administrator", acotado a ese environment)** → seguía vacío, probado tanto con API key como con JWT de sesión (se descartó que fuera un problema de método de auth).
4. Se investigó `/api/roles` → devolvió `[]`. Conclusión: los roles granulares (Environment administrator, Read-only, Operator, Helpdesk) son función de **Portainer Business Edition**; en Community Edition la API los acepta guardar pero no los aplica.
5. Se investigó Resource Control (`/api/resource_controls`, no soporta GET) y los contenedores no tienen decoración de ownership — son de un `docker-compose` corrido directo en el host, fuera de Portainer, así que no hay entrada de resource control que los haga "públicos" para usuarios no-admin.

**Conclusión:** en esta versión de Portainer CE (2.39.6), solo un administrador global ve los contenedores via el proxy de Docker. No hay forma nativa de darle a `mcp-agent` un rol verdaderamente de solo lectura a nivel Portainer.

## Decisión final
`mcp-agent` se volvió **administrador global de Portainer** (`role: 1`) — es la única configuración que funciona en la práctica. El límite de "solo lectura" se mueve a donde sí podemos garantizarlo: **el código**. `docker_tools.py` solo define `list_docker_containers()` y `get_docker_container_status()` — ninguna tool de escritura existe en el módulo, sin importar que la cuenta subyacente pueda técnicamente más (start/stop/restart de contenedores, gestión de stacks, etc. via la misma API). Mismo principio que el `hide_when_gated` de Diagnostician en devops-multiagent: si la capa de abajo no puede garantizar el límite, se garantiza una capa arriba.

## Verificado (2026-08-28)
- `list_docker_containers()` y `get_docker_container_status(name)` devuelven datos reales: `tailscale`, `adguardhome`, `portainer`, los 3 `running`, 4 días de uptime.
- Confirmado desde una sesión headless nueva de Claude Code (`mcp__proxmox__list_docker_containers`) — mismo servidor MCP ya registrado (`claude mcp add proxmox`), no hizo falta re-registrar nada porque las tools nuevas viven en el mismo `MCPServer` instance (`docker_tools.py` importa `mcp` desde `server.py`).
- Tools originales de Proxmox (`list_nodes`, etc.) siguen funcionando sin cambios tras la extensión.

## Nota operativa: password reseteado varias veces durante el debugging
Durante la investigación se reseteó el password de `mcp-agent` en Portainer varias veces (necesario para probar JWT de sesión, ya que Portainer no deja a un admin generar tokens para otro usuario — cada quien genera los suyos autenticado como sí mismo). El password final no se guardó ni se necesita — de aquí en adelante todo el acceso es por API key (`PORTAINER_API_KEY`), no por password.
