- **Nextcloud:** cliente `nextcloud-client` está instalado pero sin configurar (verificado — sin config en `~/.config/Nextcloud` ni carpeta de sync). Se decide **no** configurarlo todavía: la bitácora vive versionada en este repo (docs-as-code) y la sincronización con Nextcloud se resuelve más adelante, probablemente con el agente leyendo directo vía API/WebDAV en vez de un sync de carpeta duplicado (para evitar dos fuentes de verdad).

## Corrección sobre la infraestructura
Al probar `list_containers` se descubrió que el LXC 101 se llama **"docker-host"**, no LXCs individuales para Portainer/AdGuard. Es decir, Portainer, AdGuard Home y Tailscale corren como contenedores Docker *dentro* de ese LXC, no como LXCs propios de Proxmox. Corregido en la documentación de infraestructura.

## Nota sobre el SDK de MCP
`mcp[cli]` instaló la v2.x del SDK oficial, que renombró `FastMCP` → `MCPServer` (import: `from mcp.server.mcpserver import MCPServer`, en vez de `from mcp.server.fastmcp import FastMCP`). La API del decorador `.tool()` y `.run()` es idéntica, solo cambia el nombre de la clase y el path de import. Guía de migración: https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver

## Fase 2 — power management con guardrails

### Decisión de alcance
Se decidió **no** poner en lista negra el LXC 101 (`docker-host`, corre AdGuard/Tailscale/Portainer): Tailscale ahí ya está configurado con auto-start al reiniciar (configurado previamente por el usuario), así que el riesgo de dejarlo inaccesible es bajo. Guardrail acordado: incluirlo en las tools de escritura, pero solo tocarlo (start/stop/restart) cuando sea realmente necesario — no como parte de pruebas rutinarias.

### Separación de credenciales (el diseño clave)
Dar el rol nuevo directamente al usuario `mcp-agent@pve` habría hecho que el token de **lectura** (sin privilege separation, hereda del usuario) ganara también capacidad de escritura — rompiendo el aislamiento. Solución: rol custom `MCPPowerOperator` (privilegio único: `VM.PowerMgmt`) asignado como **API Token Permission** directamente al token `mcp-agent@pve!mcp-agent-write` (con privilege separation **activada**), no al usuario. El token de lectura queda intacto.

Verificado en vivo: llamar `nodes.get()` con el token de escritura devuelve datos recortados (sin cpu/mem/uptime) porque no tiene `Sys.Audit` — confirma que el aislamiento de permisos es real, no solo teórico.

### Tools nuevas (v0.2)
- `start_resource(node, vmid, resource_type)`
- `stop_resource(node, vmid, resource_type)` — usa `shutdown` (ordenado), no `stop` (force).
- `restart_resource(node, vmid, resource_type)` — usa `reboot`.

Sin acciones masivas — siempre un `vmid` explícito.

### Auditoría
Cada llamada a una tool de escritura escribe una línea JSON en `docs/audit/actions.jsonl` (timestamp UTC, acción, node, vmid, resource_type, resultado), generada automáticamente por el servidor, no a mano.

### Guardrails en capas (de mayor a menor)
1. Principio de menor privilegio: el token de escritura solo puede `VM.PowerMgmt`, nada de config/allocate/delete.
2. Aprobación de Claude Code por cada llamada a tool no pre-autorizada (ya viene del host, gratis).
3. Log de auditoría append-only, versionado en el repo.
4. Criterio del agente: no reiniciar 101 salvo necesidad real (acordado con el usuario, no es un control técnico — queda anotado aquí para que quede explícito).

### Prueba en vivo (2026-08-28)
Con confirmación explícita del usuario, se ejecutó `restart_resource('batman01', 100, 'lxc')` sobre Nextcloud (`batmancloud-app`), elegido por no afectar DNS/Tailscale de la LAN. Resultado:
- UPID devuelto: `UPID:batman01:...:vzreboot:100:mcp-agent@pve!mcp-agent-write:` — confirma que la acción se ejecutó con el token de escritura correcto.
- Verificado por polling con `get_resource_status`: el contenedor volvió a `status: running` con `uptime: 6` segundos.
- `docs/audit/actions.jsonl` registró la acción automáticamente: `{"ts": "...", "action": "reboot", "node": "batman01", "vmid": 100, "resource_type": "lxc", "result": "ok"}`.
