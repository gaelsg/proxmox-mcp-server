# 2026-08-28 — Arranque del proyecto

## Contexto
Objetivo general: dejar de "chatear con IA" y construir agentes que resuelvan problemas reales sobre infraestructura propia (workstation CachyOS + Proxmox VE "batman01"), como base de portafolio DevOps/AI engineering.

Fase 1 elegida: un servidor MCP de solo lectura contra la API de Proxmox, como práctica antes de dar capacidades de escritura a un agente.

## Decisiones
- **Lenguaje:** Python — SDK oficial de MCP maduro + `proxmoxer` para la API de Proxmox.
- **Gestor de proyecto:** `uv` (instalado vía pacman, repo `cachyos-extra-znver4`, v0.12.7). Reemplaza venv+pip manual.
- **Ubicación:** `~/projects/proxmox-mcp-server`, repo git inicializado por `uv init --package`.
- **Dependencias iniciales:** `mcp[cli]`, `proxmoxer`, `requests` (+ `python-dotenv` como dependencia transitiva de `mcp[cli]`, usada para cargar `.env`).
- **Secretos:** `.env` (gitignored), plantilla en `.env.example`. Nunca credenciales en el código ni en el repo.
- **Nextcloud:** cliente `nextcloud-client` está instalado pero sin configurar (verificado — sin config en `~/.config/Nextcloud` ni carpeta de sync). Se decide **no** configurarlo todavía: la bitácora vive versionada en este repo (docs-as-code) y la sincronización con Nextcloud se resuelve más adelante, probablemente con el agente leyendo directo vía API/WebDAV en vez de un sync de carpeta duplicado (para evitar dos fuentes de verdad).

## Herramientas del servidor (v0.1, solo lectura)
- `list_nodes()`
- `list_vms(node)`
- `list_containers(node)`
- `get_resource_status(node, vmid, resource_type)`

## Corrección sobre la infraestructura
Al probar `list_containers` se descubrió que el LXC 101 se llama **"docker-host"**, no LXCs individuales para Portainer/AdGuard. Es decir, Portainer, AdGuard Home y Tailscale corren como contenedores Docker *dentro* de ese LXC, no como LXCs propios de Proxmox. Corregido en la documentación de infraestructura.

## Nota sobre el SDK de MCP
`mcp[cli]` instaló la v2.x del SDK oficial, que renombró `FastMCP` → `MCPServer` (import: `from mcp.server.mcpserver import MCPServer`, en vez de `from mcp.server.fastmcp import FastMCP`). La API del decorador `.tool()` y `.run()` es idéntica, solo cambia el nombre de la clase y el path de import. Guía de migración: https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver

## Verificado (2026-08-28)
Las 4 herramientas probadas directamente contra el cluster real (`batman01`):
- `list_nodes()` → nodo `batman01` online, cpu ~0.2%.
- `list_containers('batman01')` → LXC 100 `batmancloud-app` (running), LXC 101 `docker-host` (running). Sin VMs QEMU.
- `get_resource_status('batman01', 101, 'lxc')` → status/uptime/cpu/mem correctos.
